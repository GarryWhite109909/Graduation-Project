## 二、架构总览

```text
输入代码文件
  │
  ▼
Stage 1 静态工具层（并行，近零成本）──────────────┐
  ├─ Semgrep taint（整文件，含污点路径）            │
  ├─ TaintTracker（AST 轻量污点，交叉验证）          │
  └─ Prefilter（正则，高置信命中/放行）              │
                            │                       │
                            ▼                       │
                      候选 Finding 列表              │
                      合并去重 + 归一化               │
                            │                       │
                ┌───────────┴───────────┐           │
             无候选（多数文件）         有候选（少数文件）│
                │                       │           │
                ▼                       ▼           │
          直接判安全                    对每个 finding    │
          记录 tool 召回监控          构造 triage prompt  │
                │                      │             │
                │                      ▼             │
                │               Stage 2 LLM 裁决层        │
                │               逐 finding 判真伪          │
                │               上下文：切片 + 污点         │
                │               N 次采样 → 自一致率置信度    │
                │                      │                 │
                └──────────┬───────────┘                 │
                           ▼                             │
                   结构化结果（verdict + 置信度 + 证据链 + 修复）
```

**关键反转**：LLM 的任务从"在全文中发现漏洞"（开放生成）变为"对具体 finding 判定真伪"（封闭判别）。LLM 只介入有候选的少数文件。

## 四、核心数据结构（two_stage_scanner.py）

```python
@dataclass
class ToolFinding:
    """Stage 1 产出的候选 finding（统一结构）。"""
    rule_id: str            # semgrep check_id / taint_tracker 类型 / prefilter 规则名
    category: str           # "sast" / "taint" / "prefilter"
    source: str             # 污染源（如 request.args.get('uid')）
    sink: str               # 危险点（如 cursor.execute(query)）
    taint_type: str         # SQL Injection / Command Injection / ...
    source_line: int
    sink_line: int
    path: list[str]         # 传播链（source→...→sink），跨函数时含函数名
    severity: str           # critical/high/medium/low
    tool: str               # semgrep / taint_tracker / prefilter
    evidence: str           # 原始证据文本（供 LLM 参考）

@dataclass
class AdjudicationVerdict:
    """单个 finding 的裁决结果。"""
    confirmed: bool                 # 是否判为真漏洞（多数票）
    confidence: float               # 自一致率 = 判真票数 / N
    votes_true: int
    votes_false: int
    votes_invalid: int
    reasoning: str                  # 首个判真模型的分析
    fix_suggestion: str
    raw_outputs: list[str]          # N 次采样原始输出

@dataclass
class TwoStageResult:
    """两阶段扫描的文件级结果。"""
    filename: str
    language: str
    has_vulnerability: Optional[bool]
    stage1: dict                    # 工具层统计（findings 数、各工具发现数）
    findings: list[ToolFinding]     # 全部候选
    adjudications: list[AdjudicationVerdict]  # 每个候选的裁决
    reviewer_findings: list[dict]   # 低置信需人工复核的项
    total_duration: float
```

最终 `has_vulnerability` 聚合规则（triage 阶段）：
- 任一 finding 裁决 `confirmed=True` → 文件判漏洞 True
- 全部 finding 裁决 `confirmed=False`，或无候选 → 文件判 False
- 有 finding 但全部裁决 `invalid`（解析失败）→ 保守判 None（需复核）

## 五、Stage 1：静态工具层

### 5.1 Semgrep taint 整文件召回（核心新增）

**动机**：长文件切片后，chunk A 的 source 与 chunk B 的 sink 被割裂。正确解法不是缝合 chunk，而是**对原始整文件跑一次 Semgrep taint**，把完整污点路径注入裁决上下文（方法论 §3.1）。

**Semgrep taint 规则**（示例 `sqli_taint.yaml`）：

```yaml
rules:
  - id: python-sqli-taint
    mode: taint
    options:
      taint_assume_safe_functions: true
    pattern-sources:
      - pattern: request.GET.get(...)
      - pattern: request.form.get(...)
      - pattern: request.json
      - pattern: input(...)
    pattern-sinks:
      - patterns:
          - pattern-inside: |
              cursor.execute(...)
          - pattern: $SQL
    message: "用户可控输入($VAR)流入 SQL 执行($SINK)"
    languages: [python]
    severity: ERROR
```

**运行方式**：`semgrep --json --config <rules_dir> <file>`，对整文件输出带回污点路径的 finding。

### 5.2 ExternalScanner 新增 `scan_taint()`

```python
def scan_taint(self, path: str, language: str = "python") -> list[ExternalFinding]:
    """对整文件跑 Semgrep taint 规则，返回带污点路径的 finding。
    需要 semgrep 已安装；不可用则返回空列表。
    """
```

新增常量 `_TAINT_RULES_DIR = os.path.join(os.path.dirname(__file__), "semgrep_rules")`，运行 `semgrep --json --quiet --config <dir> <path>`。

解析时除 `check_id/path/start.line/extra` 外，额外从 `extra.metavars` 提取 source/sink 实际表达式与传播链，填充 `ToolFinding.source/sink/path`。

### 5.3 三种工具合并去重

`TwoStageScanner._stage1_recall()` 并行调用：
1. `external_scanner.scan_taint()` → semgrep findings
2. `taint_tracker.trace()` → 自研污点路径（已有 [taint_tracker.py](file:///d:/code/毕业设计/Graduation-Project/graduation_project/taint_tracker.py#L265-L317)）
3. `prefilter.scan()` → 高置信命中作为候选（不再短路即终判，改为进裁决层）

去重键：`(taint_type, normalized_source, normalized_sink)`。Semgrep 与 TaintTracker 命中同一流时保留一条，标注 `tool="semgrep+taint_tracker"`。

## 六、Stage 2：LLM 裁决层

### 6.1 裁决 prompt（prompts.py 新增 `build_triage_prompt`）

```python
def build_triage_prompt(
    finding: ToolFinding,
    code_context: str,        # 切片后的相关函数 + 上下文头
    language: str = "python",
    rag_context: Optional[str] = None,
) -> str:
    """构造 finding 裁决 prompt：封闭二分类，带证据链锚点。"""
```

Prompt 结构：
```text
【安全分析任务：裁决一个静态工具告警是否为真漏洞】

静态工具报告了一个可疑代码流，请判定它是否为真实漏洞（is_confirmed）。

可疑数据流：
- 规则: python-sqli-taint
- 污染源: request.GET.get('uid')  (line 12, views.py)
- 危险点: cursor.execute(query)   (line 34, db.py)
- 传播链: request.GET.get('uid') -> query -> cursor.execute(query)

相关代码片段（已切片聚焦）：
```python
<code_context>
```

判定要求：
1. 确认 source 是否真的用户可控、sink 是否真的危险。
2. 检查 source→sink 之间是否有**有效**防御（参数化查询/转义/白名单）。
3. 若判定为真漏洞，输出 is_confirmed=true 并给出简洁 reason 与修复建议；
   否则 is_confirmed=false。

在回答最后输出如下 JSON：
```json
{"is_confirmed": true/false, "reason": "...", "fix_suggestion": "..."}
```
```

**system prompt**：沿用 `self.system_prompt`（`get_prompt_for_model(model)`，v9max→BASE_PROMPT），与主扫描一致。

### 6.2 自一致率置信度（N 次采样）

```python
def _adjudicate_one(self, finding, code_context) -> AdjudicationVerdict:
    prompt = build_triage_prompt(finding, code_context, ...)
    votes_true = votes_false = votes_invalid = 0
    raw_outputs = []
    for _ in range(self.n_samples):      # N=5
        result = self.client.generate(
            prompt=prompt,
            system_prompt=self.system_prompt,
            temperature=self.temperature,   # >0，如 0.7，保证采样多样性
            max_tokens=1024,
            num_ctx=self._num_ctx,
        )
        raw_outputs.append(result["text"])
        verdict = parse_triage_verdict(result["text"])
        if verdict is None: votes_invalid += 1
        elif verdict is True: votes_true += 1
        else: votes_false += 1
    return AdjudicationVerdict(
        confirmed=votes_true > votes_false,
        confidence=votes_true / self.n_samples,
        ...
    )
```

**置信度映射到最终结论**：
- `confirmed=True` 且 `confidence >= 0.8` → 自动记为漏洞
- `confirmed=True` 且 `0.5 <= confidence < 0.8` → 记漏洞但标记"需人工复核"
- `confirmed=False` 且 `confidence >= 0.8` → 判安全
- `confirmed=False` 且 `0.5 <= confidence < 0.8` → 判安全但标记"需人工复核"
- 低置信（`confidence < 0.5` 或平票）→ `reviewer_findings`，不自动结论

> 说明：方法论 §3.3 用 temperature>0 采样做自一致率。现有 [llm_client.py generate()](file:///d:/code/毕业设计/Graduation-Project/graduation_project/llm_client.py#L118-L259) 已支持 `temperature` 参数，基础设施可直接复用。

### 6.3 切片上下文（解决跨 chunk 割裂）

对每个 finding，用 [CodeSlicer](file:///d:/code/毕业设计/Graduation-Project/graduation_project/code_slicer.py) 把源码切片，**只取包含 source/sink 行的 chunk** 作为裁决上下文（而非全文件），聚焦 LLM 注意力。跨 chunk 的 source/sink 由 Stage 1 的整文件 taint 路径补全，无需缝合 chunk。

## 七、新增端点（main.py）

```python
class TwoStageRequest(BaseModel):
    code: str = Field(..., max_length=MAX_CODE_CHARS)
    language: str = "python"
    filename: str = "pasted_code.py"
    n_samples: int = Field(5, ge=1, le=10)   # 自一致率采样次数
    use_rag: Optional[bool] = None

@app.post("/api/analyze/two-stage")
async def analyze_two_stage(req, request):
    # HIGH 优先级，走调度器（与旧 analyze 一致，避免抢占串行 Ollama）
    _, future = scheduler.submit(
        priority, client_id,
        lambda: TwoStageScanner(...).scan_code(code, language, filename, n_samples, use_rag),
        description=f"two-stage:{req.filename}",
    )
    result, err = await _await_scan(future)
    if err: return err
    return result_to_dict(result)
```

`TwoStageScanner` 复用 `Scanner.client`（同一推理后端，避免重复加载模型），并通过 `model_registry.get_prompt_for_model` 取 system prompt。

## 九、风险与说明

1. **Semgrep taint 规则覆盖度**：初期只有 SQLi/Cmdi 两条规则。缺的 CWE 由 TaintTracker 兜底召回，且 P2 的抽样复核会回流新规则。方法论已声明这是可接受局限。
2. **自一致率 ≠ 校准概率**：它度量输出稳定性而非真实正确率。文档与前端展示须用"一致性置信度"表述（方法论 §6.4）。
3. **N 次采样延迟**：有候选文件裁决延迟 = N×单次推理。批量场景靠 vLLM continuous batching 摊薄（挖掘，不在 P1）。
4. **decision 边界**：无候选直判安全有工具层漏报风险，P1 仅记录 `tool_recall_monitor` 计数，抽样复核放 P2（方法论 §3.4）。
