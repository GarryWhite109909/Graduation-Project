# 第5章 网络安全专用模型训练(草稿)

> 本章记录从 Qwen2.5-Coder-7B 切换到 Qwen3-8B 后的训练主线。原 KnItLM 继续预训练 + Prompt Distillation 路线(2026-07-22 前)已归档,不再作为论文主路线。当前主路线为:Qwen3-8B 零样本基线 → P0 parse_fail 修复 → P1 CVE-fix 真实集校准 → P2 SFT 数据迭代(v2→v6) → P3 DPO 尝试(本地失败) → v5 最终模型。

---

## 5.1 基座切换动机与 P0/P1 重构

### 5.1.1 为什么放弃 Qwen2.5-Coder-7B 路线

2026-07-22 之前,本项目在 Qwen2.5-Coder-7B-Instruct 上完成了 Phase 1~3 的训练探索,包括:

- **Phase 1 lr × rsLoRA sweep**:发现 7B 基座在 90% 以上高准确率基座上,学习率更像"过拟合旋钮"而非"性能旋钮",最优 dev_loss 配置反而使 FPR 上升 11.5pp。
- **Phase 2 r=32 扩容**:LoRA rank 从 8 提升到 32 并未带来 strict_recall 改善,CWE 错标数维持 32,反而让 FPR 暴涨 19.2pp,证明**单纯增容不是知识注入**。
- **Phase 3 KnItLM CPT**:通过继续预训练注入 CVE/CWE/OWASP 知识,strict_recall 从 41% 提升到 64%(+23pp),FPR 从 11.5% 降到 3.8%(-7.7pp),但引入"参数化查询幻觉"副作用,4 个样本从 TP/TN 退化为 FN/FP。

更根本的问题在于:

1. **baseline 数据被 parse_fail 蒙蔽**:早期 87 段评估中 parse_fail 高达 18/87,安全样本被当作无效排除,导致 FPR 虚低约 13 个百分点。
2. **CVE-fix 测试集标签错误**:最早的 30 个 CVE-fix 样本来自同一依赖更新 commit,与真实漏洞无关,无法作为 held-out 泛化测试。
3. **训练数据与 Qwen3 不匹配**:手写 CoT 基于 Qwen2.5 的 chat template 和输出风格,与 Qwen3-8B 的 thinking 模式不兼容。

因此,2026-07-22 决定将 exp_06 训练基座切换为 **Qwen3-8B-Instruct**,原 Phase 1-3 结果归档到 `experiments/exp_06_finetune/results/_archive_qwen25/` 与 `outputs/_archive_qwen25_7b/`,不再参与后续对比。

### 5.1.2 P0:parse_fail 修复与新锚点确立

切换基座后,第一步不是训练,而是修复评估基础设施。Qwen3-8B 在 `max_tokens=1024` 时,对长 CoT 样本容易出现输出截断,导致 `parse_fail` 高达 18/87,掩盖真实指标。将 `max_new_tokens` 提升到 2048 后,parse_fail 归零,真实问题暴露:

**表 5-1 Qwen3-8B baseline 修复前后对比(87 段合成集)**

| 指标 | max_tokens=1024(旧) | max_tokens=2048(新锚点) | 变化 |
|---|---|---|---|
| parse_fail | 18/87 | 0/87 | -18 |
| recall | 0.978 | 0.967 | -1.1pp |
| FPR | 0.154 | 0.269 | +11.5pp |
| accuracy | 0.747 | 0.897 | +15.0pp |
| strict_recall | - | 0.459 | 新暴露 |

> 数据来源:`experiments/exp_06_finetune/results/exp_06_eval.ollama_qwen3_8b.20260722_000125.json` 与 `exp_06_eval.ollama_qwen3_8b.20260722_225944.json`

关键发现:
- parse_fail 不是 prompt/解析问题,而是输出长度截断;修 prompt 无法解决,提高 max_tokens 即可。
- 旧 baseline 的"低 FPR"是假象——安全样本因 parse_fail 被排除,导致 7 个 FP 中有相当一部分未被统计。
- 新锚点 **recall 0.967 / FPR 0.269 / strict_recall 0.459 / parse_fail 0/87** 成为后续所有训练评估的对比基准。

### 5.1.3 P1:CVE-fix 真实集校准合成集可信度

为验证合成集是否虚高,用 `prepare_cve_fix_testset.py` v2 策略从 NVD 按 CWE 搜索 CVE,提取真实 GitHub commit 修复前代码,构建 8 样本真实 CVE-fix 测试集。Qwen3-8B baseline 在 8 样本上的结果如下:

**表 5-2 Qwen3-8B baseline 在合成集与 CVE-fix 真实集上的对比**

| 测试集 | 样本数 | recall | accuracy | strict_recall | parse_fail |
|---|---|---|---|---|---|
| 87 段合成集 | 87 | 0.967 | 0.897 | 0.459 | 0/87 |
| 8 段 CVE-fix | 8 | 0.375 | 0.375 | 0.125 | 0/8 |

> 数据来源:`experiments/exp_06_finetune/results/exp_06_eval.ollama_qwen3_8b.20260723_001648.json`

**结论**:合成集 recall 比 CVE-fix 高出 59.2pp,严重虚高。真实 CVE 的漏洞模式更隐蔽,模型容易被防御措施迷惑(如 LdapEncoder)、将危险合理化为安全(如 eval "上下文安全")、未识别信任边界绕过(如 loopback)或缺乏跨文件数据流分析(如 pickle.loads 在另一文件)。后续 SFT/DPO 必须在 CVE-fix 上验证,不能只看合成集指标。

### 5.2.3 v2:直接复用旧数据的验证

v2 使用为 Qwen2.5-Coder-7B 准备的 `train_chatml_v2.jsonl`(823 条),主要验证旧数据是否兼容 Qwen3-8B chat template。结果显示:

- 合成集 recall 持平(0.967),未突破 0.95 红线。
- FPR 从 0.269 降到 0.231(-3.8pp),有小幅改善。
- strict_recall 从 0.459 提升到 0.623(+16.4pp),CWE 归因能力显著增强。
- CVE-fix recall 从 0.375 提升到 0.625(+25pp),证明训练数据对真实 CVE 也有泛化作用。

但 CVE-fix strict_recall 仍为 0.125,5 个 TP 中 4 个 CWE 标错,说明 SFT 提升了"判对方向"但未提升"CWE 精确归因"。

### 5.2.4 v3:CoT 重写与 CWE 统一

v3 针对 v2 的问题做了三项改造:

1. **CWE 标注统一**:修正 SSTI(CWE-94→CWE-1336)、NoSQL(CWE-643→CWE-943)、eval(CWE-94→CWE-95)等 36 条冲突标注。
2. **CoT 重写**:用 Ollama qwen3:8b 重写 107 条模板化 CoT,移除 "可能"、"潜在" 等 hedge 短语。
3. **LDAP 补充**:新增 9 条 LDAP 注入样本,试图修复 CVE-fix 中 LDAP 相关 FN。

v3 在合成集上表现更好(recall 0.984 / FPR 0.192),但在 CVE-fix 上 recall 从 0.625 回退到 0.500,`cve_fix_0003.py`(eval 代码注入)从 TP 变为 FN。根因是重写后的 CoT 更"清单式"——逐项检查 SQL/XSS/CMD 等标准类型,对非标准模式(如 calculate() 内嵌 eval())反而迟钝。**CoT 清单化对合成集标准模式更准,对真实 CVE 隐蔽模式更钝**。

### 5.2.5 v4:反清单式 prompt 与 CWE-441 补充

v4 针对 v3 的清单化问题,修改 `prompts.py` 的 `ANALYSIS_SCOPE` 为数据流推理导向,并添加"严禁逐项列举漏洞类型做排除式检查"指令;同时补充 7 条 CWE-441 信任边界绕过样本(loopback/XFF/内部 API 无认证)。

v4 评估结果(合成集 recall 0.885 / FPR 0.115 / strict_recall 0.492)看似比 v3 差,但更严重的问题是**训练数据与测试集存在系统性内容泄漏**。审计发现:

- 3 个测试样本与训练样本精确匹配。
- 63 个 v4 训练样本与 20+ 测试文件存在 30% 以上行级 Jaccard 重叠。
- 反复出现的变体(如 `safe_03_subprocess_list`、`typical_04_path`、`hard_bypass_04_path_regex`)教会模型"看到 subprocess 列表参数 → 安全"等错误模式。

因此 v4 指标不可信,**已被 v5 替代**,相关 adapter 保留在 `outputs/lora_r8_a16_e3_lr0.0001_s42_rsloraqwen3_8b_sft_p2_v4/best/` 作为历史记录。

### 5.2.6 v5:清洗泄漏样本后的首个可信基线

v5 从 v4 中删除 100 条泄漏/近泄漏样本(3 精确匹配 + 63 高重叠变体 + 34 中度重叠),并新增 10 条弱密码学样本(DES/AES 硬编码密钥/IV、CBC 模式固定 IV)。清洗后训练样本从 839 降到 749。

| 测试集 | TP | FP | FN | TN | recall | FPR | accuracy | strict_recall |
|---|---|---|---|---|---|---|---|---|
| 87 段合成集 | 61 | 6 | 0 | 20 | 1.000 | 0.231 | 0.931 | 0.590 |
| 7 段 CVE-fix | 4 | 0 | 3 | 0 | 0.571 | - | 0.571 | 0.143 |

> 数据来源:`experiments/exp_06_finetune/results/v5/exp_06_eval.finetuned_custom.20260726_085555.json`(合成集)、`experiments/exp_06_finetune/results/v5/exp_06_eval.finetuned_custom.20260726_234541.json`(CVE-fix)

**关键结论**:
- v5 是**首个可信评估基线**:v3/v4 因训练-测试泄漏导致指标不可信,v5 清洗后 recall 1.000 为真实可信值。
- 合成集 recall 1.000 不是"成就"——v5 仅比 v3 多 1 个 TP,主要贡献是可信度。

## 5.3 DPO 尝试与本地硬件约束

### 5.3.1 DPO 动机

P2 最佳模型 v5 的 FPR 为 0.231,远高于 8% 目标。DPO(Direct Preference Optimization)通过 preference pairs 让模型学习"chosen(正确拒绝)"优于"rejected(模型实际 FP 输出)",是降低 FPR 的自然选择。已准备好的 DPO 数据包括:

- `dpo_preference_pairs_v3.jsonl`:98 条通用偏好对。
- `dpo_v3_expansion.jsonl`:36 条长尾 CWE 扩展。
- `dpo_preference_pairs.jsonl`:62 条 v1 原始偏好对。
- `dpo_fp_pairs_v5.jsonl`:6 条基于 v5 真实 FP 构造的偏好对。
- `dpo_merged.jsonl`:104 条合并去重后的最终 DPO 数据。

### 5.3.2 三次尝试与失败根因

在本地 AMD Radeon RX 9060 XT 16 GB 上进行了三次 DPO 尝试,全部失败:

**表 5-7 DPO 本地失败记录**

| # | 配置 | 结果 | 根因 |
|---|---|---|---|
| 1 | 8bit + max_len=1024 | OOM 黑屏 | 8B 8bit + DPO 双前向(policy + reference)超 15GB VRAM |
| 2 | fp16 + max_len=512 | 立即 OOM | 8B fp16 本身就超 16GB |
| 3 | 4bit + max_len=512 | 跑完但 grad_norm=0 | 4bit NF4 + DPO 双前向梯度回传失效,loss=ln(2) 不下降,所有 DPO 指标归零;dmesg 记录 amdgpu drm panic |

> 失败产物归档:`outputs/_archive_dpo_failed_4bit_grad_zero/`

**根因分析**:
- DPO 需要 policy 和 reference 两个模型同时前向传播,显存需求接近 SFT 的两倍。
- 8B 模型 8bit 量化后激活/权重仍占 ~15GB,加上 optimizer states 和 reference 模型,16GB 显存不足。
- 4bit NF4 量化虽能放下两个模型,但梯度无法正确回传到 LoRA 层,导致训练无效。
- 这是 ROCm/bitsandbytes 与 DPO 双前向在消费级 16GB GPU 上的硬约束,非参数可解。

### 5.3.3 替代尝试:v6 hard-negative SFT

DPO 不可行后,改为用 SFT hard-negative 降 FPR。具体做法是将 v5 的 6 个 FP 的正确拒绝 CoT 作为正样本追加到训练集。结果已在 5.2.7 节给出:FPR 小幅下降但 recall 和 CVE-fix 泛化受损,最终失败。

### 5.3.4 后续选项

当前 DPO 数据已就绪,若换用 24GB+ GPU 或云实例可直接复用。后续有三个可行方向:

1. **云 GPU 跑 DPO**:使用 `dpo_merged.jsonl` 在 24GB/48GB GPU 上训练,目标 FPR 0.231→<8%。
2. **单个 FP micro-finetune**:针对 6 个 FP 中的某一个,用极小学习率(如 1e-5)和短 epoch(1)做 micro-finetune,但风险仍高,需严格评估。
3. **接受 v5 为最终模型**:停止训练优化,进入系统开发与论文写作,将 DPO 失败作为"局限性"与未来工作。

### 5.4.2 持续错题根因分类

v5 在 7 段 CVE-fix 中仍有 3 个 FN,自 v2 起持续未解:

**表 5-9 v5 在 CVE-fix 上的持续 FN**

| 文件 | CWE | 根因分类 | 说明 |
|---|---|---|---|
| `cve_fix_0001.java` | CWE-90(LDAP 注入) | 被防御措施迷惑 | 看到 `LdapEncoder` 就认为输入已被安全编码,忽略后续拼接 |
| `cve_fix_0002.js` | CWE-90(LDAP 注入) | 注意力偏移 | 模型关注 bcrypt 密码逻辑,忽略 LDAP 查询拼接 |
| `cve_fix_0005.js` | CWE-441(信任边界绕过) | 缺失模式识别 | loopback 信任反模式未在训练数据中出现 |

这三类 FN 共同指向**训练数据缺失真实漏洞模式**:LDAP 注入和信任边界绕过在合成集中样本不足,模型无法学到其判定边界。这解释了为什么合成集 recall 可达 1.000,而 CVE-fix recall 仅 0.571。

### 5.4.3 CWE 归因错误分析

v5 在 61 个合成集漏洞样本中检出 61 个(TP),但其中 25 个 CWE 标错,strict_recall 仅 0.590。典型错误模式:

- **eval 代码注入**:模型常标为 CWE-78(命令注入)或 CWE-94(代码注入),与 ground truth CWE-95 混淆。
- **信任边界绕过**:模型常标为 CWE-20(输入校验)或 CWE-330(弱随机),而非 CWE-441。
- **Java 反序列化**:仅 `cve_fix_0007.py` 1 例 strict_TP,其余即使检出也错标 CWE。

这说明 SFT 有效提升了二值检出能力,但**CWE 精确归因仍依赖预训练知识**。当训练数据中的 CWE 标注统一与模型预训练知识冲突时,预训练知识占主导(如 eval→CWE-95 统一后,`cve_fix_0004` 仍标 CWE-94)。

## 5.5 方法论反思与局限性

### 5.5.1 主要结论

1. **QLoRA SFT 在消费级 16GB GPU 上可行且有效**:Qwen3-8B 4bit QLoRA r=8 可在 ~3.5 小时内完成训练,显著提升 strict_recall(+13.1pp)和 CVE-fix 泛化(+19.6pp),同时保持 recall 不低于红线 0.95。
2. **数据可信度比指标绝对值更重要**:v4 因训练-测试泄漏产生漂亮但不可信的指标;v5 清洗后指标更可信,也更能指导后续决策。
3. **DPO 在 16GB 消费级 GPU 上不可行**:8bit OOM、4bit 梯度失效,这是硬件硬约束。偏好优化需要 24GB+ 显存或云实例。
4. **简单 hard-negative SFT 得不偿失**:为降 FPR 而追加安全样本正确拒绝 CoT,会导致模型对安全模式过度敏感,牺牲 recall 和真实 CVE 泛化。

### 5.5.2 局限性

- **硬件限制**:本地 16GB GPU 无法运行 DPO,限制了 FPR 优化空间。
- **CVE-fix 样本量小**:当前有效 CVE-fix 样本仅 7 条,统计意义弱,可能无法稳定反映模型泛化能力。
- **CWE 归因瓶颈**:strict_recall 0.590 仍未达 70% 目标,训练数据中的 CWE 统一未能完全覆盖预训练知识冲突。
- **训练数据模式缺失**:LDAP 注入、信任边界绕过等真实漏洞模式在训练数据中覆盖不足,导致 CVE-fix 持续 FN。

### 5.5.3 未来工作

- **云 GPU 跑 DPO**:用已准备的 `dpo_merged.jsonl` 在 24GB+ GPU 上验证 DPO 能否将 FPR 降到 8% 以下。
- **扩充真实 CVE-fix 数据**:将 CVE-fix 测试集从 7 条扩展到 20 条以上,增强统计可信度。
- **针对性补充缺失模式**:补充 LDAP 注入、信任边界绕过、跨文件数据流样本,修复持续 FN。
- **错题闭环**:在更大显存或云实例支持下,运行评估→提取错题→分类→增强→重训→再评估的闭环(max 2 轮,30% replay)。
