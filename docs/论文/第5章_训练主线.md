# 第5章 网络安全专用模型训练

> 本章记录从 Qwen2.5-Coder-7B 切换到 Qwen3-8B 后的训练主线,以及"本地探索 → 云端放大"双轨演进。原 KnItLM 继续预训练 + Prompt Distillation 路线(2026-07-22 前)已归档,不再作为论文主路线。当前主路线为:Qwen3-8B 零样本基线 → P0 parse_fail 修复 → P1 CVE-fix 真实集校准 → **本地 QLoRA SFT 迭代(v2→v9)** → **三模型 API 蒸馏数据规模化** → **云端 A800 训练 v9max 并发布**。v9max 是已发布的关键里程碑,最终模型 Nivis-alpha.1 将在其基础上完成偏好优化与数据飞轮后收敛。

---

## 5.1 基座切换动机与 P0/P1 重构

### 5.1.1 为什么放弃 Qwen2.5-Coder-7B 路线

2026-07-22 之前,本项目在 Qwen2.5-Coder-7B-Instruct 上完成了 Phase 1~3 的训练探索,包括:

- **Phase 1 lr × rsLoRA sweep**:发现 7B 基座在 90% 以上高准确率基座上,学习率更像"过拟合旋钮"而非"性能旋钮",最优 dev_loss 配置反而使 FPR 上升 11.5pp。
- **Phase 2 r=32 扩容**:LoRA rank 从 8 提升到 32 并未带来 strict_recall 改善,CWE 错标数维持 32,反而让 FPR 暴涨 19.2pp,证明**单纯增容不是知识注入**。
- **Phase 3 KnItLM CPT**:通过继续预训练注入 CVE/CWE/OWASP 知识,strict_recall 从 41% 提升到 64%(+23pp),FPR 从 11.5% 降到 3.8%(-7.7pp),但引入"参数化查询幻觉"副作用,4 个样本从 TP/TN 退化为 FN/FP。

更根本的问题在于:

1. **baseline 数据被 parse_fail 蒙蔽**:早期 87 段评估中 parse_fail 高达 18/87,安全样本被当作无效排除,导致 FPR 虚低约 13 个百分点。
2. **CVE-fix 测试集标签错误**:最早的 30 个 CVE-fix 样本来自同一依赖更新 commit,与真实漏洞无关,无法作为 held-out 泛化测试。
3. **训练数据与 Qwen3 不匹配**:手写 CoT 基于 Qwen2.5 的 chat template 和输出风格,与 Qwen3-8B 的 thinking 模式不兼容。

因此,2026-07-22 决定将 exp_06 训练基座切换为 **Qwen3-8B-Instruct**,原 Phase 1-3 结果归档到 `experiments/exp_06_finetune/results/_archive_qwen25/` 与 `outputs/_archive_qwen25_7b/`,不再参与后续对比。

### 5.1.2 P0:parse_fail 修复与新锚点确立

切换基座后,第一步不是训练,而是修复评估基础设施。Qwen3-8B 在 `max_tokens=1024` 时,对长 CoT 样本容易出现输出截断,导致 `parse_fail` 高达 18/87,掩盖真实指标。将 `max_new_tokens` 提升到 2048 后,parse_fail 归零,真实问题暴露:

**表 5-1 Qwen3-8B baseline 修复前后对比(87 段合成集)**

| 指标 | max_tokens=1024(旧) | max_tokens=2048(新锚点) | 变化 |
|---|---|---|---|
| parse_fail | 18/87 | 0/87 | -18 |
| recall | 0.978 | 0.967 | -1.1pp |
| FPR | 0.154 | 0.269 | +11.5pp |
| accuracy | 0.747 | 0.897 | +15.0pp |
| strict_recall | - | 0.459 | 新暴露 |

> 数据来源:`experiments/exp_06_finetune/results/exp_06_eval.ollama_qwen3_8b.20260722_000125.json` 与 `exp_06_eval.ollama_qwen3_8b.20260722_225944.json`

关键发现:
- parse_fail 不是 prompt/解析问题,而是输出长度截断;修 prompt 无法解决,提高 max_tokens 即可。
- 旧 baseline 的"低 FPR"是假象——安全样本因 parse_fail 被排除,导致 7 个 FP 中有相当一部分未被统计。
- 新锚点 **recall 0.967 / FPR 0.269 / strict_recall 0.459 / parse_fail 0/87** 成为后续所有训练评估的对比基准。

### 5.1.3 P1:CVE-fix 真实集校准合成集可信度

为验证合成集是否虚高,用 `prepare_cve_fix_testset.py` v2 策略从 NVD 按 CWE 搜索 CVE,提取真实 GitHub commit 修复前代码,构建 CVE-fix 真实测试集。先期 7 条有效样本,后于 2026-07-31 扩展到 20 条。Qwen3-8B baseline 在 8 样本上的结果如下:

**表 5-2 Qwen3-8B baseline 在合成集与 CVE-fix 真实集上的对比**

| 测试集 | 样本数 | recall | accuracy | strict_recall | parse_fail |
|---|---|---|---|---|---|
| 87 段合成集 | 87 | 0.967 | 0.897 | 0.459 | 0/87 |
| 8 段 CVE-fix | 8 | 0.375 | 0.375 | 0.125 | 0/8 |

> 数据来源:`experiments/exp_06_finetune/results/exp_06_eval.ollama_qwen3_8b.20260723_001648.json`

**结论**:合成集 recall 比 CVE-fix 高出 59.2pp,严重虚高。真实 CVE 的漏洞模式更隐蔽,模型容易被防御措施迷惑(如 LdapEncoder)、将危险合理化为安全(如 eval "上下文安全")、未识别信任边界绕过(如 loopback)或缺乏跨文件数据流分析(如 pickle.loads 在另一文件)。后续 SFT 必须在 CVE-fix 上验证,不能只看合成集指标。

## 5.2 本地 QLoRA SFT 迭代(v2→v9)

### 5.2.1 统一训练配置

所有本地 Qwen3-8B SFT 实验采用统一配置,仅数据文件不同:

**表 5-3 Qwen3-8B 本地 SFT 统一训练配置**

| 配置项 | 取值 |
|---|---|
| 基座模型 | Qwen/Qwen3-8B |
| 量化 | 4bit NF4 + double quant |
| LoRA rank | 8 |
| LoRA alpha | 16 |
| LoRA dropout | 0.1 |
| rsLoRA | 启用 |
| DoRA | 关闭 |

> 训练环境:AMD Radeon RX 9060 XT 16 GB / ROCm 7.2.4 / PyTorch 2.11.0+rocm7.2

### 5.2.2 本地迭代结果总览

**表 5-4 Qwen3-8B 本地 SFT 版本迭代结果对比**

| 版本 | 训练样本 | 核心变更 | 合成集 recall | 合成集 FPR | 合成集 strict_recall | CVE-fix recall | 状态 |
|---|---|---|---|---|---|---|---|
| baseline | - | - | 0.967 | 0.269 | 0.459 | 0.375(8样本) | 锚点 |
| v2 | 823 | 直接复用 Qwen2.5 时代数据 | 0.967 | 0.231 | 0.623 | 0.625 | 首个可信 SFT |
| v3 | 832 | 36 条 CWE 统一 + 107 条 CoT 重写 + LDAP 补充 | 0.984 | 0.192 | 0.607 | 0.500 ⚠️ | CoT 清单化副作用 |
| v4 | 839 | 反清单式 prompt + CWE-441 补充 | 0.885 | 0.115 | 0.492 | 0.429 | ❌ 训练-测试泄漏,废弃 |

本地 8 轮迭代(v2~v9)揭示了四条关键方法论教训,每一轮都对应一个可复现的数据/训练陷阱:

1. **v4 数据泄漏**:63 个训练样本与 20+ 测试文件存在 30% 以上行级 Jaccard 重叠,教会模型"看到 subprocess 列表 → 安全"等错误模式。引入 **Jaccard 泄漏审计**后,清洗出 100 条泄漏/近泄漏样本,得到首个可信基线 v5。
2. **v6 hard-negative 负迁移**:将 FP 的正确拒绝 CoT 作为正样本追加训练,虽降低了 1 个 FP,却让模型对安全代码过度敏感,真实 CVE 上新增 1 个 FN、召回率下降 14.2pp。**单纯追加负样本得不偿失**。
3. **v7 手工样本拉高假象**:新增 13 条手工真实 CVE 样本全部命中,把整体 recall 拉高到 0.800,但复查发现原 7 条真实 CVE 上实际仅 0.429。**Bootstrap 显著性检验**(配对 block bootstrap, N=10000)确认 v7 与 v5 在合成集上无显著差异,改进主要在真实 CVE 泛化而非合成集。
4. **v8 对比 CoT 判别焦虑**:教"CWE-89 vs CWE-90"的反事实对比 CoT,反而让模型在边界上纠结到误判安全,FP 从 6 增至 8,strict_accuracy 全面退步。**训练样本不得含"无漏洞但建议改进"的矛盾信号,epochs 不得超过 best checkpoint**。

### 5.2.3 v2~v5:数据质量与可信度爬坡

v2 直接复用为 Qwen2.5-Coder-7B 准备的 823 条数据,验证旧数据对 Qwen3-8B chat template 的兼容性。结果显示 strict_recall 从 0.459 提升到 0.623(+16.4pp),CVE-fix recall 从 0.375 提升到 0.625(+25pp),证明 SFT 有效提升了方向判定与 CWE 归因;但 CVE-fix strict_recall 仍为 0.125,5 个 TP 中 4 个 CWE 标错。

v3 聚焦 CWE 标注统一(36 条,SSTI→CWE-1336、NoSQL→CWE-943、eval→CWE-95)与 107 条模板化 CoT 重写。v3 在合成集上更好(recall 0.984 / FPR 0.192),但 CVE-fix recall 从 0.625 回退到 0.500——重写后的 CoT 更"清单式",对非标准模式(如 `calculate()` 内嵌 `eval()`)反而迟钝。**CoT 清单化对合成集标准模式更准,对真实 CVE 隐蔽模式更钝**。

v4 修改 prompt 为数据流推理导向并补充 CWE-441 信任边界样本,但因训练-测试系统性能泄漏,指标不可信,被 v5 替代。v5 从 v4 中删除 100 条泄漏/近泄漏样本,并新增 10 条弱密码学样本,是**首个可信评估基线**(recall 1.000 / FPR 0.231 / strict_recall 0.590)。但 v5 的 6 个 FP 暴露了模型对防御机制的理解缺陷,如将 `subprocess.run(["ping","-c","1",host])` 的列表形式误解为字符串拼接、忽略 `shlex.quote` 的防御作用。

### 5.2.4 v7~v9:实战泛化与云端过渡

v7 以 v5 为基底,针对 CVE-fix 持续 FN 的三个盲区(CWE-90 LDAP / CWE-441 信任边界 / CWE-190 整数溢出)新增 50 条样本,并加入反事实 CoT、对比 CoT。v7 在 **20 段扩展 CVE-fix 真实集**上 recall 达 0.800、strict_recall 达 0.650,是首个在真实 CVE 上取得质的飞跃的模型;但合成集 recall 微降到 0.983,且 4 个持续 FN 根因(v2 起未解)仍指向训练数据缺失真实漏洞模式与跨文件数据流分析。

v8 转向 strict_accuracy 优先策略,新增 24 条对比 CoT 样本,却因判别焦虑全面退步。v9 基于 v8 失败诊断做三管齐下修正:替换矛盾信号样本、新增 5 条 v8 FP 靶向安全样本、补充易混 CWE 边界,并将 epochs 从 3 收敛到 2。v9 数据扩到 914 条,但本地 16 GB 显存与手写数据量的瓶颈已经显现——**进一步提升需要大规模数据与全精度算力,这成为转向云端的直接动因**。

## 5.3 本地 DPO 尝试与硬件约束

### 5.3.1 DPO 动机

P2 最佳模型 v7 的 FPR 为 0.231,远高于 8% 目标。DPO(Direct Preference Optimization)通过 preference pairs 让模型学习"chosen(正确拒绝)"优于"rejected(模型实际 FP 输出)",是降低 FPR 的自然选择。已准备好的 DPO 数据包括 `dpo_merged.jsonl`(104 条合并去重)、`dpo_fp_pairs_v5.jsonl`(6 条基于 v5 真实 FP 构造的偏好对)等。

### 5.3.2 三次尝试与失败根因

在本地 AMD Radeon RX 9060 XT 16 GB 上进行了三次 DPO 尝试,全部失败:

**表 5-5 本地 DPO 失败记录**

| # | 配置 | 结果 | 根因 |
|---|---|---|---|
| 1 | 8bit + max_len=1024 | OOM 黑屏 | 8B 8bit + DPO 双前向(policy + reference)超 15GB VRAM |
| 2 | fp16 + max_len=512 | 立即 OOM | 8B fp16 本身就超 16GB |
| 3 | 4bit + max_len=512 | 跑完但 grad_norm=0 | 4bit NF4 + DPO 双前向梯度回传失效,loss=ln(2) 不下降,所有 DPO 指标归零;dmesg 记录 amdgpu drm panic |

> 失败产物归档:`outputs/_archive_dpo_failed_4bit_grad_zero/`

**根因**:DPO 需要 policy 和 reference 两个模型同时前向传播,显存需求接近 SFT 的两倍。8B 模型 8bit 量化后仍占 ~15GB,加上 optimizer states 与 reference 模型,16GB 显存不足;4bit NF4 虽能放下两个模型,但梯度无法正确回传到 LoRA 层。这是 ROCm/bitsandbytes 与 DPO 双前向在消费级 16GB GPU 上的硬约束,非参数可解。

### 5.3.3 硬件约束对训练路线的决定性影响

三次 DPO 失败与 v9 的数据量瓶颈共同指向同一结论:**消费级 16GB GPU 只能支撑中等规模的 QLoRA SFT,无法承担偏好优化与大规模数据训练**。这直接决定了"本地探索 → 云端放大"的双轨策略:本地利用便携算力低成本、快速验证数据与方法论,云端则释放全精度 bf16 与大规模数据的能力。

## 5.4 三模型蒸馏与云端训练 v9max

### 5.4.1 三模型 API 蒸馏数据规模化

为突破本地手写数据量(峰值 914 条)的瓶颈,采用 **DeepSeek V4-Flash / Kimi K3 / GLM-5.2 三模型 API 蒸馏**生成大规模训练数据(提示词方案见 `docs/v9max_数据生成提示词.md`):

**表 5-6 三模型蒸馏分工**

| 模型 | 目标条数 | 覆盖域 |
|---|---|---|
| DeepSeek V4-Flash | 7700 | C/C++ 内存漏洞 / 渗透命令注入 / Web 漏洞 / Shell 配置 / 漏洞修复 |
| Kimi K3 | 2000 | C/C++ 内存重构 / 跨文件分块审计(长上下文调用链) |
| GLM-5.2 | 1500+ | CWE+CVSS 严格格式 / 负样本(格式锚) |

蒸馏遵循三条铁律:CoT ≤ 5 步 ≤ 590 token、三段式统一输出、负样本 1:3 配比。原始目标合计约 11200 条,但经 CWE 归一化、CWE 命名标准化、Jaccard 泄漏审计、清除矛盾/重复样本后,最终得到用于训练的 `final_train_chatml_quality_final.jsonl` **7692 条**(漏洞 3493 / 安全 4199,安全占比 54.6%)。实测 CWE 分布 top:CWE-89 SQL(243)、CWE-78 OS 命令(210)、CWE-798 硬编码凭证(199)、CWE-79 XSS(170)、CWE-22 路径(162);语言分布:Python 2385 / C 1306 / JS 1148 / shell 1127 / Java 1005 / PHP 564 / Go 497 / SQL 366 / C++ 347。

> 计划量→实际量的差距(约 11200→7692)说明蒸馏数据必须经过严格清洗才能用于训练,数量不等于质量。

### 5.4.2 云端 A800 训练

数据合并清洗后,训练迁移到云端 **A800 GPU**(bf16 全精度,突破 16GB 限制):

**表 5-7 v9max 云端训练配置与结果**

### 5.4.3 发布:量化与 Ollama 部署

v9max 评估达标后,通过 `tools/release_model.sh` 发布:merge LoRA → 转 HF 格式 → 转 GGUF f16 → 量化为 **Q4_K_M**(约 4.7 GB,适配 8 GB 显存)→ `ollama create`。发布的关键改进:

- Ollama 模型:`garrywhite109909/graduation-vuln-scanner:v9max`(5.0 GB Q4_K_M)。

由于 Modelfile 硬编码了专用 SYSTEM,v9max 收敛为**专用代码安全审计模型**,不再进行通用对话——这是预期的定位,而非缺陷。

v9max 在真实 CVE 上 recall 达 0.95,较 v7 的 0.800 再提升 15pp,相对 baseline 的 0.375 提升 57.5pp。仅剩 1 个 FN(`cve_fix_0003.py`,PraisonAI A2A server 将 `calculate(expression)` 注册到未认证 JSON-RPC 的远程可控 RCE)——模型识别到 `eval()` 却将其合理化为"封装在函数里、非直接用户输入",属"识别到危险但合理化为安全"类 FN,与 v2 起持续存在的根因一致。

### 5.5.3 FPR 上升的根因:模式匹配 > 深度理解

v9max 合成集 FPR 从 baseline 的 0.269 恶化到 0.423,10 个净 FP 的主因不是训练数据不足(安全样本占 54.6%),而是**模型对防御机制的理解错误**。溯源 11 个 FP 的 raw_output 发现三类典型误判:

1. **`safe_03_subprocess_list.py`**:`subprocess.run(["ping","-c","1",host])` 是安全写法(列表 = 独立 argv,shell 元字符不被解释),模型却断言"参数是直接拼接的",把列表形式误解成字符串拼接。
2. **`safe_08_shlex.py`**:`shlex.quote` 正是防 shell=True 注入的手段,模型承认转义了,却仍说"shell=True 可能允许特殊字符执行额外命令"——**不知道 shlex.quote 的作用**。
3. **`safe_04_path_whitelist.py`**:模型识别出了白名单 + abspath 双重防御,却用"abspath 行为可能因平台不同而异"合理化判漏洞——**过度怀疑**。

剔除 1 个跨文件 input 层的标注设计问题样本后,净 FPR ≈ 10/26 ≈ 0.385,仍高于 baseline。模型学到的是"看到危险函数名就报"(subprocess.run / shell=True / open),没有学会"判断数据流是否真的能到危险点"。CWE 分布 top 是 CWE-89/78/798,命令注入类训练样本最多,模型对"用户输入→subprocess"模式训得很足形成条件反射。

**这两类评估结果共同说明**:v9max 在"检出能力"上已达到发布水准(漏报清零、真实 CVE recall 0.95),但"FPR 抑制"与"CWE 精确归因"仍需后续偏好优化与防御机制教学来收敛。

## 5.6 最终模型定位:Nivis-alpha.1

v9max 是漏洞检出能力大幅增强的**已发布里程碑**,但不是训练主线的终点。基于 v9max 的评估缺口(FPR 0.423、strict_recall 0.607、`cve_fix_0003` 类 FN),最终模型 **Nivis-alpha.1** 将在 v9max 基础上完成以下收敛:

1. **DPO 偏好优化**:在云端 A800 上运行,用模型对安全样本的真实错误推理作为 rejected、正确判定含 CoT 作为 chosen,针对性压 FPR。本地 16 GB 已证 DPO 不可行,云端 bf16 全精度可复用本地已备的 `dpo_merged.jsonl`。
2. **GRPO**:可选,通过奖励函数强化"带防御→判安全"的细粒度策略,但工程成本高,作为可选路径。
3. **数据飞轮 + CoT 教学**:补充"防御机制教学 CoT"(教"为什么安全"),根治"模式匹配 > 深度理解"——这是比 DPO 更治本的方向。
4. **攻克 `cve_fix_0003` 类 FN**:训练数据补充"eval 封装在函数但仍远程可控"反模式。
5. **提升 fix_usable**:改进 FixVerifier 危险模式检测覆盖面。

Nivis-alpha.1 收敛后,将作为整套系统的最终交付模型,并完成 DPO/GRPO/数据飞轮/CoT 的完整方法论闭环。

## 5.7 方法论反思与局限性

### 5.7.1 主要结论

1. **QLoRA SFT 在消费级 16GB GPU 上可行且有效**:Qwen3-8B 4bit QLoRA r=8 可在数小时内完成训练,显著提升 strict_recall 与真实 CVE 泛化,同时守住 recall 0.95 红线。
2. **数据可信度比指标绝对值更重要**:v4 因训练-测试泄漏产生漂亮但不可信的指标;v5 清洗后指标更可信,也更能指导后续决策。Jaccard 泄漏审计与 Bootstrap 显著性检验是本地迭代的必备把关手段。
3. **"本地探索 → 云端放大"是消费级硬件下可行的工程路线**:本地可用数据量与显存双受限,但足以低成本验证数据/方法论;规模突破需三模型蒸馏 + 云端 A800 全精度训练,二者互补。
4. **DPO 在 16GB 消费级 GPU 上不可行**:8bit OOM、4bit 梯度失效,偏好优化需要 24GB+ 显存或云实例。
5. **简单 hard-negative 与对比 CoT 均得不偿失**:为降 FPR 追加安全样本正确拒绝 CoT,会导致对安全模式过度敏感;对比 CoT 引发判别焦虑。应以"多样安全代码 + 防御机制教学"替代。

### 5.7.2 局限性

- **FPR 偏高**:v9max 合成集 FPR 0.423,根因是模型对防御机制的理解缺陷,需 DPO/CoT 教学收敛。
- **CWE 归因瓶颈**:strict_recall 0.607 仍未达 70% 目标,模型对不熟悉 CWE 存在归因偏置(倾向归为 CWE-89/79/200/798)。
- **CVE-fix 样本量有限**:20 条真实样本统计意义有限,`cve_fix_0003` 类隐蔽 FN 仍存在。
- **硬件约束**:本地无法跑 DPO,偏好优化只能依赖云端资源。

### 5.7.3 未来工作

- **完成 Nivis-alpha.1**:云端 DPO/GRPO、数据飞轮 + CoT 教学,收敛 FPR 与 CWE 归因。
- **扩充真实 CVE-fix 数据**:增强统计可信度,覆盖更多 CWE 与语言。
- **改进修复代码可用性**:提升 `fix_usable`,让模型修复建议达到可直接应用的工程水准。
- **系统集成与多语言扩展**:将 Nivis-alpha.1 接入 CI/CD 流水线并扩展多语言覆盖。
